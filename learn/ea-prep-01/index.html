Solution Architect · Interview prep

Enterprise architect prep

Do six study sessions this weekend. Part 1 gives one card per technology in the job description. Part 2 takes the questions a Solution Architect panel is likely to ask, explains what each one tests, and gives a model answer. On the morning of the interview, read only the cheat sheet.

What these interviews test Senior architecture interviews often follow one pattern. The panel starts with a scenario, then asks "what else?" until you run out. Then they follow your answer into the next layer: "you scaled Kafka, so what happens to the database?" Be ready for three things:
  • End-to-end thinking. A change in one layer moves the bottleneck to the next layer. Say this before they ask.
  • Completeness. Have a checklist ready (the 6 Cs), so "what else?" never stalls you.
  • Direct answers with numbers. Answer the question in your first sentence. Then give volumes, partition counts, latencies. Panels drop candidates who talk around a question.
  • Options under constraint. When a dependency cannot scale, never stop at "the other team is not ready". Give options, trade-offs and an escalation path.

01 · Messaging backbone

Apache Kafka

Kafka is a distributed, append-only commit log. Producers write records to topics. Each topic splits into partitions. Brokers store partitions on disk and replicate them. Consumers read at their own pace and track their position with offsets.

Why use it: it decouples producers from consumers in time and in speed. Data stays on disk after it is read, so you can replay it. It scales horizontally by adding partitions and brokers. It is the default backbone for high-volume event-driven systems.

Core mechanics

  • Partition = unit of order and parallelism. Order is guaranteed only inside one partition.
  • Key decides partition: murmur2(key) % partitions. Same key, same partition, same order. A null key spreads records (sticky partitioner).
  • Consumer group: each partition goes to exactly one consumer in the group. Consumers above the partition count sit idle.
  • Replication: RF=3, min.insync.replicas=2, acks=all. Survives one broker loss with no data loss.
  • Retention by time or size. Log compaction keeps the latest value per key (good for state topics).

Delivery semantics

  • At-most-once: commit before processing. Can lose data.
  • At-least-once: process, then commit. Can duplicate. This is the normal choice, with idempotent consumers.
  • Exactly-once: idempotent producer plus transactions plus isolation.level=read_committed. Holds only for Kafka-to-Kafka. An external database still needs idempotent writes.
  • Idempotent producer is on by default since Kafka 3.0 ver. It keeps order with up to 5 in-flight requests.

Operations to know

  • Consumer lag is the key health metric. Measure it in seconds, not only in messages.
  • Rebalance: if processing takes longer than max.poll.interval.ms (default 5 min), the consumer is removed and its partitions move. Use cooperative-sticky assignment and static membership (group.instance.id) to reduce churn. Kafka 4.0 made the new consumer rebalance protocol (KIP-848) generally available ver.
  • KRaft: Kafka 4.0 (March 2025) removed ZooKeeper. Metadata now lives in a Raft quorum in Kafka ver.
  • Queues for Kafka (share groups, KIP-932): lets many consumers share one partition with per-message acknowledgement. Preview in 4.1 (Sept 2025). Check its status before you mention it ver.
  • Throughput tuning: producer linger.ms, batch.size, compression.type (lz4 or zstd). Consumer max.poll.records, fetch.min.bytes.
  • On Azure: Event Hubs has a Kafka-protocol endpoint (Standard tier and above). Other options: Confluent Cloud on Azure, or self-managed with Strimzi on AKS.
Gotchas
  • You cannot reduce partitions. Adding partitions changes the key-to-partition mapping, so order breaks for existing keys during the change.
  • Kafka has no built-in DLQ for plain consumers. Spring Kafka and Kafka Connect add one.
  • Retry topics break per-key order.
  • A hot key puts all its load on one partition. More partitions do not help it.
  • Too many partitions per broker slow down failover and use more memory and file handles.
Say this"Kafka gives me ordering per key, durable buffering and replay. I size partitions for peak throughput and maximum consumer parallelism, with headroom, because I cannot shrink them later and growing them remaps keys."

02 · Patterns

Event-driven architecture patterns

Event-driven architecture (EDA) means services communicate by publishing facts ("OrderPlaced") instead of calling each other directly. The JD asks for "event modeling, topic strategy, schema evolution, idempotency, retries, dead-letter handling, replay, and observability". This card covers each one.

Why use it: loose coupling, absorbing traffic spikes (load levelling), independent scaling, and an audit trail you can replay.

Gotchas
  • A DLQ is for bad messages, not for an outage. If the downstream is down, pause and keep the data in Kafka. Do not flood the DLQ.
  • Retries without jitter cause a retry storm that knocks the recovering service down again.
  • Event sourcing is not the same as EDA. Do not propose it unless audit or temporal queries need it.
Say this"I design for at-least-once delivery and make every consumer idempotent. Outbox on the write side, idempotency on the read side, DLQ only for poison messages."

03 · Data

Apache Cassandra

Cassandra is a distributed, wide-column NoSQL database. It has no leader: every node is equal. Data spreads across a token ring by hashing the partition key. It is built for very high write volume, linear scale-out and multi-datacenter active-active.

Why use it: predictable low-latency writes at scale, no single point of failure, tunable consistency, and built-in multi-region replication. Use it for known access patterns such as time series, messages, events, user activity. Do not use it for ad-hoc queries, joins or multi-row transactions.

Data modeling rules

  • Query first. List access patterns, then design one table per query. Denormalize. No joins.
  • Primary key = partition key (where the data lives) + clustering columns (sort order inside the partition).
  • Every query must give the full partition key. ALLOW FILTERING is a design smell.
  • Bound partition size. Keep partitions well under 100 MB (aim for about 10 MB). Use time buckets: ((customer_id, month), sent_at).
  • Avoid hot partitions: spread load across many keys.

Consistency and replication

  • NetworkTopologyStrategy, RF=3 per datacenter.
  • Strong reads when R + W > RF. With RF=3: QUORUM write (2) + QUORUM read (2) = 4 > 3.
  • Multi-region: use LOCAL_QUORUM to avoid cross-region latency.
  • Repair mechanisms: hinted handoff, read repair, and scheduled anti-entropy repair (nodetool repair, or Reaper).
  • Writes are upserts, so replaying the same write is idempotent. Counters and list appends are not.

Internals that explain performance

  • Write path: commit log + memtable, flushed to immutable SSTables. Writes are cheap.
  • Read path: may merge many SSTables (bloom filters help). Reads cost more than writes.
  • Compaction strategy: STCS for write-heavy, LCS for read-heavy, TWCS for time series with TTL. Cassandra 5.0 adds Unified Compaction Strategy (UCS) and Storage-Attached Indexes (SAI) ver.
  • Lightweight transactions (IF NOT EXISTS) use Paxos. They cost about 4 round trips. Use sparingly.
  • Distributions: DataStax Enterprise (DSE) and Astra DB are commercial Cassandra offerings. IBM completed its acquisition of DataStax in 2025 ver. Cassandra 5.0 is the current major line as of this check ver.
  • On Azure: Azure Managed Instance for Apache Cassandra (real Cassandra), or Azure Cosmos DB for Apache Cassandra (CQL-compatible API, priced in request units).
Gotchas
  • Tombstones. Deletes and TTL expiry write tombstones. Many tombstones in one read cause slow reads and then failures (default fail threshold is 100,000). Using Cassandra as a queue is the classic anti-pattern.
  • Run repair within gc_grace_seconds (default 10 days), or deleted data can come back.
  • Multi-partition unlogged batches are slower, not faster. Logged batches give atomicity, not speed.
  • Materialized views are experimental. Secondary indexes on high-cardinality columns perform poorly; SAI is better but still not free.
Say this"I model Cassandra from the access patterns. Partition key for distribution, clustering key for sort, time buckets to bound partition size, LOCAL_QUORUM for consistency in a multi-region setup, and TWCS with TTL for time series."

Sources: Cassandra docs: data modeling; Cassandra 5.0 what's new; Azure Managed Instance for Apache Cassandra. Checked 23 Oct 2026.

04 · Platform

Kubernetes and AKS

Kubernetes (K8s) runs containers across a cluster of machines. You declare the desired state in YAML. Controllers keep the actual state equal to it. Azure Kubernetes Service (AKS) is the managed version: Azure runs the control plane, you run the node pools.

Why use it: one standard platform for deploy, scale, self-heal, roll out and roll back, across many teams.

Objects to know

  • Deployment (stateless), StatefulSet (stable identity and disk), DaemonSet, Job/CronJob.
  • Service: ClusterIP, NodePort, LoadBalancer. Ingress or Gateway API for HTTP routing.
  • ConfigMap and Secret. A Secret is only base64, not encrypted. On AKS use Key Vault with the Secrets Store CSI driver.
  • Probes: startup, readiness (take out of traffic), liveness (restart).
  • Requests/limits: requests drive scheduling. A CPU limit throttles. A memory limit kills (OOMKilled).
  • PodDisruptionBudget, topology spread across zones, anti-affinity.
  • NetworkPolicy, RBAC, ServiceAccount, namespaces.

Scaling

  • HPA: scales pods on CPU, memory or custom metrics.
  • KEDA (AKS add-on): scales on events, for example Kafka consumer lag. Set max replicas = partition count.
  • Cluster Autoscaler or Node Auto-Provisioning (Karpenter-based) adds nodes. Nodes take minutes, so keep headroom.
  • VPA for right-sizing suggestions. Do not run VPA and HPA on the same metric.

AKS specifics

  • System and user node pools. Spread across availability zones. Use the Standard tier for the uptime SLA.
  • Networking: Azure CNI Overlay is the usual default now. Plain Azure CNI gives each pod a VNet IP, so subnets run out of IPs.
  • Workload Identity (federated with Entra ID) replaces the deprecated pod-managed identity.
  • Private cluster, egress through Azure Firewall, GitOps with the Flux extension.

Troubleshooting shortlist

Pending = no capacity, or taints/affinity. CrashLoopBackOff = app crash; check kubectl logs --previous. ImagePullBackOff = registry or auth. OOMKilled = memory limit. Always start with kubectl describe pod and events.

Gotchas
  • A liveness probe that checks the database restarts every pod when the database blips. Check dependencies in readiness only, or not at all.
  • Graceful shutdown: add a preStop sleep and match terminationGracePeriodSeconds (default 30s). Otherwise rolling updates drop requests.
  • ingress-nginx was retired in March 2026. Plan for Gateway API, or Application Gateway for Containers on Azure. AKS published its own support timeline for its add-on ver.
  • Scaling pods multiplies database connections. See Q5.
Say this"On AKS I separate system and user pools across three zones, scale stateless APIs with HPA and Kafka consumers with KEDA on lag, capped at the partition count, and keep secrets in Key Vault through Workload Identity."

Sources: Kubernetes concepts; Kubernetes blog: ingress-nginx retirement (Nov 2025); AKS blog: ingress-nginx update; AKS best practices; KEDA Kafka scaler. Checked 23 Oct 2026.

06 · Backend

Java and Spring Boot

Spring Boot is the standard Java framework for microservices. It gives auto-configuration, starter dependencies, an embedded server and production features through Actuator.

Why use it: large ecosystem (Spring Security, Spring Kafka, Spring Data Cassandra), quick start, and strong operational support. Spring Boot 4.0 (Nov 2025) runs on Spring Framework 7 with a Java 17 baseline. Java 21 and 25 are the current LTS releases ver.

Points to remember

  • Actuator: health, readiness and liveness groups for K8s probes, metrics through Micrometer to Prometheus.
  • Virtual threads (Java 21+, spring.threads.virtual.enabled=true): cheap blocking I/O concurrency. They move the bottleneck to the connection pool.
  • HikariCP is the default pool. Default maximumPoolSize is 10. The pool is per JVM instance, per datasource.
  • Resilience4j: timeout, retry with backoff, circuit breaker, bulkhead, rate limiter.
  • Tomcat default max threads is 200. Request threads above pool size just wait for a connection.

Service and API design

  • Boundaries follow DDD bounded contexts. One database per service.
  • REST with OpenAPI. Errors in application/problem+json (RFC 9457). Pagination. Versioning.
  • Idempotency key header on POST, so clients can retry safely.
  • No distributed transactions across services. Use local transactions + outbox + saga.
  • Spring Security as an OAuth2 resource server. Validate JWTs from Entra ID.
Gotchas
  • @Transactional works through a proxy. A call from inside the same class skips it. By default it rolls back only on unchecked exceptions.
  • Never make a remote call inside a database transaction. It holds the connection while you wait.
  • Bigger pools are not faster. HikariCP guidance starts from cores × 2 + disks on the database side.
  • Set the JVM heap with -XX:MaxRAMPercentage so it respects the container limit.
  • Default HTTP clients may have no timeout. Always set connect and read timeouts.
Say this"Every outbound call gets a timeout, a bounded retry with jitter, and a circuit breaker. Connection pools are sized per pod, and the total across pods must fit the database limit."

07 · Front end

ReactJS front-end architecture

React is a JavaScript library for building user interfaces from components. Data flows one way, from parent to child. React compares a virtual tree and updates only what changed. The JD asks about component design, state, API integration, performance, accessibility and secure journeys.

Why use it: the largest ecosystem, reusable component design systems, and rendering options from client-only to server rendering. React 19 (Dec 2024) added Actions and stable Server Components. React Compiler 1.0 (Oct 2025) memoizes automatically. Create React App is deprecated; start with a framework such as Next.js or with Vite ver.

Architecture decisions

  • Rendering: CSR (app-like portals behind login), SSR or streaming (fast first paint, SEO), SSG (static content).
  • State, by type: local UI state (useState); server state in TanStack Query or SWR (cache, dedupe, retry); global client state in Zustand or Redux Toolkit; URL state for filters.
  • Design system: shared accessible component library, Storybook, tokens.
  • BFF (backend for frontend): shapes APIs for the UI and keeps tokens on the server.
  • Micro-frontends (Module Federation) only when many teams must deploy separately. They add cost.

Performance and accessibility

  • Core Web Vitals: LCP < 2.5 s, INP < 200 ms (INP replaced FID in March 2024), CLS < 0.1.
  • Code splitting with lazy and Suspense, bundle budgets, list virtualization, image optimization, CDN.
  • WCAG 2.2 AA: semantic HTML first, ARIA only when needed, keyboard paths, focus management on route change, colour contrast.
  • Automate checks: axe-core in CI, Lighthouse budgets.

Secure user journeys

  • OAuth 2.0 Authorization Code flow with PKCE (MSAL for Entra ID / External ID). No implicit flow.
  • Prefer a BFF with HttpOnly, Secure, SameSite cookies over tokens in localStorage (XSS can read it).
  • React escapes output. dangerouslySetInnerHTML is the XSS hole. Add a Content Security Policy.
  • Never trust the client. Authorize every API call on the server.
Gotchas
  • Putting fast-changing values in one big Context re-renders the whole tree.
  • Most "global state" is really cached server data. Treat it as a cache with invalidation.
  • An SPA route change does not move focus or announce the page to screen readers unless you do it.
Say this"For a customer portal: a framework with SSR for public pages, a shared accessible design system, server state in a query cache, a BFF for auth, and Web Vitals and axe checks as CI quality gates."

Sources: React 19 release; React Compiler 1.0; Sunsetting CRA; web.dev Core Web Vitals; WCAG 2.2. Checked 23 Oct 2026.

08 · Operations

Observability, Grafana and SRE

Observability means you can explain any system behaviour from its outputs: metrics, logs, traces (and profiles). Grafana is the dashboard and alerting layer. The Grafana "LGTM" stack is Loki (logs), Grafana, Tempo (traces) and Mimir (Prometheus-compatible metrics). OpenTelemetry (OTel) is the vendor-neutral standard for producing telemetry. Grafana Alloy is Grafana's OTel collector; Grafana Agent reached end of life on 1 Nov 2025 ver.

Why it matters here: the JD asks for an "SRE mindset" and "data transfer SLAs". You cannot defend an SLA you do not measure end to end.

SRE vocabulary

  • SLI: a measured ratio, e.g. events delivered within 5 s / all events.
  • SLO: the target, e.g. 99.9% over 30 days.
  • SLA: the contract with penalties. Set the SLO tighter than the SLA.
  • Error budget: 99.9% leaves about 43 min per 30 days. Spend it on releases; freeze when it is gone.
  • Burn-rate alerts, multi-window: page when 2% of the monthly budget burns in 1 hour (burn rate 14.4).

What to measure

  • RED for services: Rate, Errors, Duration.
  • USE for resources: Utilization, Saturation, Errors.
  • Golden signals: latency, traffic, errors, saturation.
  • Percentiles (p95, p99) from histograms. Never averages.
  • Kafka: lag in seconds, end-to-end latency from the event's origin timestamp to processed time.
  • Pools: HikariCP active, idle, pending and acquire time.
  • Trace propagation: W3C traceparent header over HTTP, and in Kafka record headers, so a trace crosses the async hop.
  • Exemplars link a metric spike to an example trace. Logs carry the trace ID.
  • Alert on symptoms users feel, not on every cause. Every page links to a runbook.
  • Synthetic probes and heartbeat events catch "nothing is flowing" when error counts are zero.
Gotchas
  • High-cardinality labels (user ID, order ID) blow up metric storage and cost.
  • Averages hide tail latency. One slow dependency shows only in p99.
  • Head-based trace sampling can drop the rare slow trace. Consider tail-based sampling.
  • Log volume is a cost line. Set retention tiers.
Say this"I define SLIs from the customer's view, instrument with OpenTelemetry including across Kafka, build RED dashboards in Grafana, and alert on error-budget burn rate rather than raw thresholds."

Sources: Google SRE Workbook: Alerting on SLOs; OpenTelemetry docs; Grafana Alloy docs; Azure Managed Grafana. Checked 23 Oct 2026.

  • Production readiness review: SLOs set, dashboards and alerts live, runbooks written, load-tested, DR tested, security sign-off, rollback proven.

BDD, Cucumber and Karate

  • BDD (behaviour-driven development): write acceptance criteria as Given / When / Then scenarios in Gherkin, readable by business and testers.
  • Cucumber: runs Gherkin scenarios. Each step needs Java "step definition" glue code.
  • Karate (open source, Karate Labs): Gherkin-style syntax built for API testing, with no step definitions to write. HTTP calls, JSON and XML assertions, and data-driven tests are built in. It can also run API mocks (useful as test doubles for partner systems), reuse API tests as performance tests through Gatling, and drive UI tests.
  • When to use which: Karate for API and integration suites owned by engineers; Cucumber where business-readable acceptance tests matter most.

Chaos engineering and blast radius

  • Method: define steady state (SLIs), state a hypothesis ("losing one broker does not breach the delivery SLO"), inject a fault, observe, fix what you learn.
  • Faults to inject: kill pods and nodes, lose a zone, add latency or errors to a downstream, kill a Kafka broker, slow Cassandra nodes, exhaust a connection pool.
  • Keep the blast radius small: start in a non-production environment, then a small slice of production (one service, one zone, canary traffic), with an automatic stop when an SLO alert fires, and run in business hours with people watching.
  • Tools: Azure Chaos Studio, Chaos Mesh, LitmusChaos.
  • Blast radius by design: bulkheads, cell-based architecture (split customers or regions into independent cells), per-tenant rate limits, and progressive rollout.
Gotchas
  • Flaky tests destroy trust in the gate. Quarantine and fix them; do not just retry.
  • Large E2E suites are slow and brittle. Keep them for the top journeys.
  • Load tests with unrealistic data (one key, warm cache) give false confidence. Hot keys and cold caches are where systems fail.
Say this"I shift testing left with Testcontainers and contract tests, keep E2E to critical journeys, and make security, accessibility and performance budgets automatic gates, not end-of-project phases."

10 · Security

Security, identity and threat modeling

Security is in almost every JD line: "secure user journeys", "identity and access", "threat modeling", partnering with cybersecurity. Base the answer on zero trust: verify every request, give least privilege, assume breach.

Identity

  • OIDC for authentication, OAuth 2.0 for authorization. Tokens are JWTs signed by Entra ID.
  • Customer sign-in: Entra External ID (successor to Azure AD B2C for new customers) ver.
  • Service-to-service: managed identity or client credentials, or mTLS through a service mesh.
  • Validate token audience, issuer, expiry and scopes in every service.

Threat modeling (STRIDE)

  • Spoofing → strong authentication
  • Tampering → signing, integrity checks
  • Repudiation → audit logs
  • Information disclosure → encryption, least privilege
  • Denial of service → rate limits, WAF, autoscale
  • Elevation of privilege → authorization checks, RBAC
  • Encrypt in transit (TLS 1.2+) and at rest. Key Vault for keys and secrets. Kafka with TLS and SASL/OAuth plus ACLs.
  • OWASP Top 10 for web, OWASP API Security Top 10 for APIs (broken object-level authorization is number one).
  • Supply chain: signed images, SBOM, dependency scanning, admission policies in AKS (Azure Policy).
  • PII in events: minimize it, or tokenize. Kafka retention and replay make "right to be forgotten" hard.

15 · Domain

Logistics and freight event platforms

A global logistics and freight company moves goods by air, ocean, road and rail, and through warehouses. Its core digital need is visibility: where is each shipment, is it on time, and what is it costing. That makes it an event-processing problem with many external sources, very uneven volume, and data that arrives late, twice or out of order.

Event sources (upstream)

  • Handheld scanners and driver mobile apps (often offline, then sync in bulk)
  • Warehouse management systems (WMS): receipt, put-away, pick, pack, dispatch
  • Transport management systems (TMS): bookings, transport legs, routing
  • Carriers and shipping lines: status updates through APIs or EDI messages (e.g. EDIFACT IFTSTA, ANSI X12 214 and 315)
  • Customer systems: orders and bookings through EDI, APIs or the portal
  • Customs, finance and billing systems

Core entities

  • Booking → shipment → one or more transport legs
  • Milestone / status event: picked up, departed, arrived, customs cleared, delivered
  • Container, pallet, package; house and master bills of lading or air waybills
  • Reference data: locations (UN/LOCODE), carrier codes, customers
  • Charges and invoices

Architectural considerations

  • Variable volume: peak season, Monday-morning backlogs, a vessel arrival that releases thousands of container events at once, carriers that send batch files every few hours. Design for bursts: Kafka buffers, consumers scale on lag.
  • Out-of-order and late events: a delivered scan can arrive before the departed scan when a device was offline. Store every event by event time; derive current status with a state machine that ignores older or impossible transitions.
  • Duplicates: carriers resend; devices retry. Dedup on (source, source event ID) and make writes idempotent.
  • Missing events: detect gaps (an expected milestone that never came, sequence gaps per source) and reconcile counts per partner per hour.
  • Canonical event model: map every source format to one internal schema at the edge (an anti-corruption layer per partner), with the raw payload kept for audit and replay.
  • Partner onboarding is constant: adapters per carrier or customer, contract tests, mocks of partner APIs.
  • Customer-facing SLA: e.g. a milestone appears in the portal and in customer notifications within N minutes of the scan.
  • Global operation: multiple regions (Americas, Europe, Asia), data residency (GDPR for EU customer data), time zones (store UTC and the local offset).

A common integration shape in this domain

  1. Source systems publish thin events to Kafka, one topic per event type, often per business line (air and ocean, road, customs brokerage): booking, booking request, transport leg, routing, milestone, scan, finance.
  2. A split service breaks a composite message (one booking with many legs or containers) into one event per entity.
  3. A consumer per event type receives the notification and fetches the full payload from the source's data store or an enterprise message hub (claim-check pattern).
  4. It maps and transforms the payload into the canonical model.
  5. It enriches it with master-data identifiers (a global customer or party ID, location codes).
  6. It publishes to target platforms through an API gateway: a unified shipment API, a finance API, an emissions (CO2) calculation service, and inbound and outbound links to external transport partners.

Practise the questions this shape raises in Q6d.

Kafka and Cassandra for this domain

  • Kafka key = shipment ID (or container ID), so events for one shipment stay in order. Watch for hot keys: a consolidated master shipment with very many child events.
  • events_by_shipment ((shipment_id), event_time, event_id): full history, newest or oldest first.
  • shipments_by_customer ((customer_id, day), updated_at DESC, shipment_id): the portal list view, bucketed by day.
  • shipment_status ((shipment_id)): latest derived status for fast lookups.
  • TTL on history according to the retention policy; TWCS compaction.

Principle: "No data is lost, because we separate accepting data from delivering it. We accept, persist durably, acknowledge, and deliver asynchronously with retries."

  2. Delivery consumer posts to the downstream API with a timeout and bounded retries using exponential backoff and jitter.

Q3 · Kafka partitions and scaling through the layers

IntentDo you understand partitions, keys and consumer groups? Then the real test: scaling Kafka consumers pushes load to the next layers. Do you know what that forces downstream? Expect "how does it affect the subsequent layers?" more than once. Most candidates stop at "add consumers".
How are partitions decided?

Two meanings. Answer both.

  • Which partition a record goes to: the producer hashes the key (murmur2(key) % partitions). Same key, same partition, so order holds per key. No key means records spread out. A custom partitioner is possible but rare.
  • How many partitions a topic gets: from target throughput and parallelism. partitions ≥ max(target throughput ÷ per-partition producer rate, target throughput ÷ per-consumer processing rate). Section 6 · Integration pipeline

Q6d · Notify, fetch, transform, enrich, publish

IntentThe panel may describe its own pipeline: thin events, a split service, consumers that fetch the full payload, map it, enrich it with master data and publish through an API gateway. Then they ask what breaks and how you would improve it. They test whether you see the hidden dependencies: the payload store, the master-data service, the target API, and ordering across topics.

Source event → split → consume → fetch payload → map → enrich → publish via API gateway → target

Why fetch the payload instead of putting it in the event? Trade-offs?

This is the claim-check (or event-notification) pattern.

  • For: small events; large or sensitive payloads stay in the source of truth; consumers always get the latest version; less PII sprayed across topics.
  • Against: every event becomes an extra synchronous call, so the payload store is now on the critical path for every consumer. Load on it multiplies with events × consumers. Replay depends on the store still holding that version.
  • Race: the event can arrive before the store has committed the data. Fetch returns "not found" or an old version. Handle with a short retry with backoff, and a version number in the event so the consumer knows which version to expect.
  • Alternative: event-carried state transfer (full payload in the event, with Schema Registry) removes the fetch. Good for high-volume, medium-sized payloads. A hybrid is common: key fields in the event, full detail by fetch.
The payload store (or message hub) is slow or down. What happens?
  • Every consumer type stalls at once: it is a shared dependency with fan-in from all flows.
  • Timeout, retry with jitter, circuit breaker, then pause the consumers. Kafka holds the events; nothing is lost within retention. Do not send them to the DLQ: the events are fine.
  • Alert on lag in seconds per flow, and on fetch latency and error rate.
  • On recovery, drain with a rate limit so the store is not knocked over again. Prioritise flows (milestones the customer sees before low-priority batch flows).
  • Design fixes: capacity plan the store for events × consumers; read replicas or a cache for hot reads; bulk fetch APIs; consider carrying more state in the event.
Enrichment fails: the master-data service has no mapping for this customer or location yet.
  • This is a data problem, not a poison message. Retrying immediately will not help, and dropping it loses data.
  • Park it in a "pending enrichment" retry topic or table with a delay, and retry on a schedule or when the master-data change event arrives.
  • Set a time limit, then raise it to the data stewardship team, with a dashboard of unmapped references by source.
  • Cache master data locally (refresh by change events, with a TTL) so the enrichment service is not called once per event.
  • Decide with the business whether a partial record (no master ID yet) may be published and corrected later.
A milestone arrives before the booking or shipment it belongs to exists in the target.

Different event types travel on different topics, so there is no ordering between them. Options:

  • Park and retry: hold the child event until the parent exists (delay topic, bounded retries, then alert).
  • Upsert with placeholder: the target accepts the milestone and creates a skeleton shipment, filled in when the booking arrives. Needs idempotent, order-tolerant target APIs.
  • Same key, same topic: put all events for one shipment on one topic keyed by shipment ID, so order holds. Costs a less clean topic design.
  • Monitor: count parked events by age; an orphan after N hours is a data-quality incident.
What does the split service change about ordering and volume?
  • Amplification: one booking with 40 containers becomes 40 events. Size downstream for the split rate, not the source rate.
  • Keys: the split service must choose the output key deliberately (shipment or container ID) so related events stay in order.
  • Atomicity: if it fails half-way, some children are published and some are not. Use the idempotent producer and transactions, or deterministic child IDs so a re-run is deduplicated.
The target API behind the gateway cannot take your peak rate.

Same answer as Q5: agree a rate with the owner, rate-limit the consumers to it, let Kafka absorb the peaks, use bulk endpoints, prioritise customer-visible flows, and escalate with data if the SLA is at risk. Gateway throttling responses (HTTP 429) must trigger backoff, not fast retries.

You have a dozen consumers that each fetch, map, enrich and publish. How do you govern that?
  • A reference implementation or shared library for the common steps: fetch with resilience, idempotency, correlation-ID propagation, metrics, DLQ and retry handling. Each consumer writes only its mapping.
  • Mapping rules as versioned, tested artefacts with contract tests against sample payloads from each source.
  • One dashboard per flow with the same panels: rate, lag in seconds, fetch latency, enrichment failures, publish errors, DLQ depth, end-to-end latency.
  • Trace context carried from the source event through split, fetch and publish, so one shipment can be followed across every hop.
How would you improve this architecture over time?
  • Move high-volume flows towards event-carried state, to remove the fetch from the hot path.
  • Reduce point-to-point consumers with a canonical shipment event that targets subscribe to.
  • Schema Registry and compatibility checks for every topic.
  • End-to-end SLOs per flow, with burn-rate alerts.
  • Do it incrementally, one flow at a time, with a parallel run and reconciliation before switching.

Section 8 · Technical scenarios

Q8 · Technical scenarios: ordering, and a sudden latency spike

Intent(a) Do you know that Kafka orders per partition and how to design for strict ordering, including retries? (b) Do you have a calm, structured triage method: impact first, mitigate, then root cause?
8a · Messages must be consumed in sequence. How do you guarantee order with Kafka?

Correct the premise politely: "Kafka does guarantee order inside a partition. So the design question is choosing the right key and keeping order through producing, consuming and failure."

  1. Key by the entity that needs order (account ID, order ID). All its events go to one partition. Most use cases need per-entity order, not global order.
  2. Producer: idempotent producer (enable.idempotence=true, acks=all, ≤5 in-flight) so retries do not reorder or duplicate.
  3. Consumer: process each partition sequentially, or parallelize by key inside the partition (key-ordered parallel consumer). Commit offsets only after processing.
  4. Failures: no retry topics for ordered streams. Use blocking retry, or park the failed message and all later messages for the same key.
  5. Defence in depth: put a sequence number or version in each event. The consumer rejects or buffers out-of-order events and ignores older versions. This also covers ordering issues from upstream.
  6. Global order across all data: only with one partition, which caps throughput at one consumer. Say this trade-off.
  7. Partition changes: adding partitions moves keys, so order can break during the change. Plan for it.

Alternative on Azure: Service Bus sessions give ordered processing per session ID.

8b · An API was fine, and suddenly latency spikes. How do you approach it?

Principle: "Impact first, mitigate fast, then find root cause. Restore service before you investigate in depth."

  1. Scope: all endpoints or one? All pods or one? All users or one tenant/region? p50 too, or only p99? When did it start?
  2. What changed: deploys, config or feature flags, traffic pattern, dependency releases, infrastructure events (node scale, AKS upgrade), certificate or secret rotation. Most incidents follow a change.
  3. Follow the traces: pick slow traces and find the slow span: our code, the database, a downstream call, or waiting for a connection or thread.
  4. Check saturation (USE): CPU throttling, GC pauses, thread pool full, connection pool pending, memory pressure, node noisy neighbour, network/DNS/SNAT.
  5. Check dependencies: database slow queries and locks; Cassandra tombstones, compaction, hot partition; cache hit rate drop or stampede; downstream API latency; Kafka lag.
  6. Mitigate: roll back the change, scale out, fail over, shed load, turn off a feature flag, open the circuit to a slow dependency.
  7. After: blameless postmortem, root cause, add the missing alert or test, track actions to done.

More questions to expect

Further questions likely from the job description. Short answers: the points to hit, not a script.

Kafka and events

Kafka and event-driven

How do you achieve exactly-once processing?

Kafka EOS (idempotent producer + transactions + read_committed) covers read-process-write inside Kafka. For external systems, use at-least-once delivery plus idempotent writes (upsert, dedup by event ID, version check). Say "effectively once".

How do you update a database and publish an event reliably?

Transactional outbox. Do not dual-write: if the publish fails after the commit, the two disagree. Outbox row in the same local transaction; Debezium CDC or a poller publishes it; consumers dedup.

How do you evolve event schemas without breaking consumers?

Schema Registry, Avro or Protobuf, BACKWARD (or FULL) compatibility enforced in CI. Add optional fields with defaults; never rename or remove in place. A breaking change gets a new versioned topic and a migration window with both versions.

Kafka vs Event Hubs vs Service Bus: when each?

Kafka/Event Hubs: high-volume streams, replay, many consumers, ordering per partition. Service Bus: transactional commands and work queues with per-message settle, DLQ, sessions, scheduled delivery, duplicate detection. Event Grid: lightweight reactive notifications (resource events, webhooks).

How do you run Kafka across two regions?

Usually one cluster per region, stretched over three zones. Replicate with MirrorMaker 2 or Cluster Linking. Decide active-passive (consumers fail over; offsets translated) or active-active (regional topics, aggregate). Producers must tolerate duplicates after failover.

How do you scale consumers automatically?

KEDA Kafka scaler on lag threshold, min replicas for warm capacity, max replicas = partition count. Watch rebalance cost; use cooperative rebalancing and static membership.

Data

Cassandra and data

Model "show a customer's last 50 messages, newest first".

CREATE TABLE messages_by_customer (customer_id uuid, bucket text, sent_at timeuuid, message_id uuid, body text, status text, PRIMARY KEY ((customer_id, bucket), sent_at)) WITH CLUSTERING ORDER BY (sent_at DESC) AND default_time_to_live = 7776000;

Partition by customer plus month bucket to bound size. Cluster by time descending so the query is one partition slice with LIMIT 50. TWCS compaction with TTL. A second table, message_by_id, for lookup by ID. Write both (logged batch if atomicity matters).

What consistency level do you use and why?

LOCAL_QUORUM for reads and writes with RF=3 per DC: strong in-region consistency, survives one node down, no cross-region latency. ONE for low-value high-volume reads. EACH_QUORUM only if a write must be confirmed in every region.

Reads are getting slow on one table. What do you check?

Large partitions, tombstone warnings in logs, SSTables per read, compaction backlog (pending compactions), hot partitions, wrong compaction strategy, GC pauses, queries using ALLOW FILTERING or secondary indexes, consistency level higher than needed.

Why Cassandra rather than Cosmos DB or PostgreSQL?

Cassandra: massive write throughput, multi-region active-active, known access patterns, open source and portable (MI on Azure). Cosmos DB: fully managed, multi-model, SLA-backed, but RU cost at high volume. PostgreSQL: relational integrity, ad-hoc queries, transactions; scales up more than out. Choose by access pattern, consistency need, scale and team skills; record in an ADR.

Integration variantMany enterprise logistics estates already run a notify-then-fetch pipeline: thin events per type → split → consumer fetches the full payload → map → enrich with master data → publish through an API gateway to target platforms. If the panel describes this, design within it, and talk about the fetch dependency, the enrichment dependency, cross-topic ordering and the target API's rate limits.

Walkthrough order (10 minutes)

  1. Clarify (1 min): volume (average, peak, burst), message size, SLA (e.g. 99.9% delivered in 5 s), ordering need, delivery guarantee, retention, regions, RTO/RPO, compliance.
  2. Ingest (1 min): Front Door + WAF, APIM for auth and throttling, stateless ingest API validates, writes to Kafka (acks=all), returns 202 with a tracking ID. Idempotency key from the client.
  3. Buffer (1 min): Kafka, RF=3 across zones, key = entity ID for order, partitions sized for peak plus growth, retention covers longest outage plus drain.
  4. Process (2 min): consumers on AKS scaled by KEDA, process idempotently, record status in Cassandra (status by message ID, messages by customer by time), deliver downstream with timeout, retry, breaker. Pause on outage; retry topics or DLT for poison messages.
  5. SLA and observability (2 min): origin timestamp, end-to-end latency SLI, lag in seconds, tracing across Kafka, burn-rate alerts, heartbeat events, Grafana SLO dashboard.
  6. Scale and failure (2 min): walk the 6 Cs, backpressure, downstream rate limits, zone and region failure, DR drills.
  7. Trade-offs (1 min): ordering vs throughput, consistency vs latency, cost of active-active, Event Hubs vs self-managed Kafka.

Cheat sheet: interview morning

Read only this before the call.

Numbers

  • 99.9% = ~43 min down per 30 days. 99.95% = ~22 min. 99.99% = ~4.3 min.
  • Series availability multiplies: 99.95% × 99.95% ≈ 99.90%.
  • Little's Law: in-flight = rate × time. Connections = q/s × query seconds.
  • Partitions ≥ peak ÷ per-consumer rate, plus growth headroom.
  • Cassandra strong: R + W > RF. RF=3 → QUORUM/QUORUM or LOCAL_QUORUM.
  • Kafka safe write: RF=3, min ISR=2, acks=all, idempotence on.
  • Hikari default pool 10; Tomcat 200 threads; max.poll.interval.ms 5 min; K8s grace 30 s; Cassandra gc_grace 10 days.
  • Web Vitals: LCP 2.5 s, INP 200 ms, CLS 0.1.
  • Burn-rate page: 2% of budget in 1 h = 14.4×.
  • 10,000 msg/s × 2 KB = 20 MB/s ≈ 1.7 TB/day before replication.

Lines to land

  • "Scaling one layer moves the bottleneck to the next."
  • "The pool is per pod. Total = pods × pool, and it must fit the database."
  • "DLQ is for poison messages, not outages. On outage, pause and let Kafka hold the data."
  • "Kafka orders per partition. Key by the entity that needs order."
  • "At-least-once delivery plus idempotent consumers."
  • "Measure the SLA end to end from the customer's view."
  • "Impact first, mitigate, then root cause."
  • "Every event is kept; status is derived by event time; every feed is reconciled."
  • "10× traffic is a capacity change in every layer, not a Kafka setting."
  • "When a dependency cannot scale: protect, level the load, negotiate, escalate with options."
