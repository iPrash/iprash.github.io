Agentic AI · Learning guide

Agentic systems: definitions, patterns and where to learn more

A general guide to agentic AI for an architect. Learn the vocabulary, the building blocks and the orchestration patterns, then how to choose between them and how to build them well. Every pattern has a diagram and an example. Part 6 lists the best free courses, videos and reading, so you can go deeper by building. Start with the simplest thing that works. Add an agent only when the task needs one.

How this site fits with the othersThis guide is general and stays useful across roles. The insurance design-phase guide, agentic-ea, applies these patterns to one domain. Read the pattern here, then see it used there.

Self-check: twelve questions

Answer aloud in under 30 seconds each. A miss sends you to the named card.

Triage

Where are the gaps?

1. What is the difference between a workflow and an agent?

In a workflow, code defines the path and LLMs fill in steps. In an agent, the LLM decides its own steps and which tools to use. Both are "agentic systems". Card 1.1.

2. What is the augmented LLM?

A model with retrieval, tools and memory attached. It is the building block for every pattern. Card 1.2.

3. Describe the agent loop in one line.

A model using tools in a loop: gather context, act, check the result, repeat until done or stopped. Card 1.3.

4. When do you use routing instead of prompt chaining?

Chaining when every input follows the same fixed steps. Routing when the type of input decides which path, model or prompt to use. Cards 2.1, 2.2.

5. What separates orchestrator-workers from parallelisation?

In parallelisation, the subtasks are fixed in advance. In orchestrator-workers, the orchestrator decides the subtasks from the input. Card 2.4.

6. What does reflection mean in Andrew Ng's patterns, and which Anthropic pattern is it?

The model critiques and improves its own output. It is close to the evaluator-optimizer pattern. Cards 2.5, 2.10.

7. Give the main argument for and against multi-agent systems.

For: parallel subagents with their own context windows do well on broad, breadth-first tasks. Against: they use many more tokens, and decisions made in separate contexts can conflict. Card 3.2.

8. What is context engineering?

Choosing and maintaining the smallest set of useful tokens in the context window: instructions, tools, examples, history and retrieved data. Long context degrades recall, so less is often more. Card 4.1.

9. Name two graders for an eval and when to use each.

Code graders for exact, checkable outputs. Model graders (LLM-as-judge) for open text, with a rubric. Add human graders to calibrate both. Card 4.4.

10. Why is prompt injection worse for agents than for chat?

An agent reads untrusted content and can act with tools. Injected text can make it misuse a tool or its privileges. Card 4.6.

11. MCP or A2A: which connects an agent to tools, and which connects agents to each other?

MCP connects agents to tools and data. A2A lets agents from different systems find each other and pass work. Card 5.1.

12. What is Microsoft's current agent framework, and what happened to AutoGen and Semantic Kernel?

Microsoft Agent Framework, 1.0 in April 2026. It is the successor to both. They now get maintenance only. Card 5.2.

1.2 · Building block

The augmented LLM

Every pattern in Part 2 is built from one unit: a model with retrieval, tools and memory around it. Get this unit right first. Clear tool descriptions and good retrieval do more for quality than adding agents.

RememberMost "agent problems" are context problems: a vague tool description, missing data, or too much noise in the window.
1.3 · Building block

The agent loop

An agent is a model using tools in a loop. It gathers context, takes an action, checks the result, and repeats. The ReAct style writes this out as thought, action and observation. A stop condition ends the loop: the task is done, a step or cost limit is hit, or a human is needed.

Sources: AI Engineer: How We Build Effective Agents (Barry Zhang) [P]; Claude Agent SDK overview [P]. Checked 18 Nov 2026.

1.4 · Choosing

The complexity ladder

Each step up the ladder adds capability, and adds cost, latency and new ways to fail. Microsoft's guidance gives the spectrum as a direct model call, a single agent with tools, then multi-agent orchestration, and says to use the lowest level that reliably meets the need. Anthropic gives the same advice: find the simplest solution and add complexity only when needed.

Say this"I start on the lowest rung that meets the requirement and move up only when a test shows I need to."

Sources: Azure Architecture Center: AI agent orchestration patterns [P]; Anthropic: Building effective agents [P]. Checked 18 Nov 2026.

1.5 · Architecture

Enterprise layers

A reference stack for an enterprise agentic system. Use it to place every component in a design review. The platform runs down the side: it gives every layer identity, guardrails, tracing, evals and cost control.

1.6 · Architecture

Agents advance business objects

A common enterprise pattern: the work is a business object that moves through states, and agents move it forward. The object holds the facts, the history and the audit trail. Agents and people read it and update it through one integration layer. This keeps agents stateless and makes every step traceable.

Why it works

  • State lives in the object, so a run can stop and resume.
  • Every change is an event, so lineage comes free.
  • Agents can be swapped without changing the object.

Watch out

  • Agree the object schemas early. They are the contract between teams.
  • Generate documents from data. Do not store the document as the only record.
1.7 · Operating model

Touch levels

Enterprises often state an automation target as a touch level: how much a person handles a case. The level drives where you put human gates and how you set confidence thresholds.

LevelWhat a person doesFits
No touchNothing for routine cases. Straight-through processing, with sampling.Simple, standard, low-value work with clear rules
Low touchApproves at one or two decision points.Standard products, mid-market
Mid touchReviews evidence and decides at several points. Agents prepare everything.Complex, high-value or specialist work
High touchDoes most of the work, with a copilot.Novel or bespoke cases
RememberOne programme can hold several touch levels. Set the level per product or line of business.

2.1 · Workflow

Prompt chaining (sequential)

Split a task into fixed steps. Each LLM call handles one step and passes its output to the next. Put a code check, a "gate", between steps to stop bad output early. You trade latency for accuracy, because each call has an easier job.

Use when

  • The steps are known and the same every time.
  • Each step can be checked.

Example

Extract a table from a document, then map its columns to a schema, then validate the values, then write the output.

Gotchas
  • One bad step spoils everything after it. Gates are not optional.
  • Latency adds up. Run independent steps in parallel instead (2.3).
2.2 · Workflow

Routing (handoff)

Classify the input, then send it to a specialised path: a different prompt, a different tool set or a different model. Routing keeps each path simple and lets cheap models take easy cases. In multi-agent frameworks the same idea appears as a handoff: one agent passes control to a specialist.

Use when

  • Inputs fall into clear categories that need different handling.
  • You want to save cost on easy cases.

Example

Route a customer message to billing, technical support or a refund flow. Route a document by type before extraction.

Gotchas
  • Measure router accuracy as its own eval. A misroute looks like a failure of the downstream path.
  • Always have a fallback route, usually a human.
2.3 · Workflow

Parallelisation (concurrent)

Run several LLM calls at once and combine the results. Anthropic names two forms. Sectioning: split the task into independent parts. Voting: run the same task several times and compare, to raise confidence.

Use when

  • Subtasks do not depend on each other.
  • Several views of the same thing raise accuracy.

Example

Screen a request for policy, fraud and compliance at the same time. Run two models on a hard classification and accept only when they agree.

Gotchas
  • Voting multiplies cost. Use it only on the hard cases.
  • Decide in advance what happens when results disagree.
2.4 · Workflow or agent

Orchestrator-workers (manager)

A central LLM breaks the task into subtasks, sends them to workers, and combines the results. It looks like parallelisation, with one key difference: the subtasks are not fixed in advance. The orchestrator decides them from the input. Microsoft's Magentic pattern is a manager agent that builds and updates a task list as it goes.

Use when

  • You cannot predict the subtasks.
  • The work is broad: many independent directions.

Example

A research task where a lead agent starts subagents to search different angles, then writes the answer. A large spreadsheet split by tab, processed in parallel, then reconciled.

Gotchas
  • Workers need enough context to do their part. A one-line task description is rarely enough.
  • Cap the number of workers, steps and tokens.

Sources: Anthropic: Building effective agents [P]; Azure: orchestration patterns (Magentic) [P]. Checked 18 Nov 2026.

2.5 · Workflow

Evaluator-optimizer (reflection)

One call produces an output. A second call grades it against criteria and gives feedback. The first call revises. Repeat until the output passes or a limit is hit. Andrew Ng calls the single-model version of this "reflection".

Use when

  • There is a clear standard to test against.
  • Feedback measurably improves the result.

Example

A drafting step writes a customer letter. A checker tests it against required wording and tone. A code generator runs unit tests and fixes failures.

Gotchas
  • Prefer code checks (tests, schema validation) over a model judge when you can.
  • Always set an iteration limit.
2.6 · Agent

The autonomous agent

The model plans and acts on its own in the loop from 1.3, using feedback from tools and its environment. It suits open problems where you cannot write the steps in advance. It costs more, takes longer, and can compound errors, so it needs strong tools, sandboxes, limits and tests.

Use when

  • The task is complex and valuable.
  • The path varies too much to code.
  • You can check the result: tests, a verifier, a human.

Example

A coding agent that reads a repository, edits files, runs tests, and repeats until the tests pass.

Gotchas
  • Errors compound over many steps. Checkpoints and human review points matter.
  • Test in a sandbox before giving real permissions.

Sources: Anthropic: Building effective agents [P]; OpenAI: A practical guide to building agents (PDF) [P]. Checked 18 Nov 2026.

2.7 · Multi-agent

Hierarchical

Orchestrator-workers, nested. A top orchestrator delegates to team-level orchestrators, each with its own workers. Google's ADK describes multi-agent systems as agents that often form a hierarchy.

Gotchas
  • Each level adds tokens, latency and a place for context to get lost. Use it only when one orchestrator cannot hold the work.

Sources: Google ADK: Multi-agent systems [P]. Checked 18 Nov 2026.

2.8 · Multi-agent

Group chat

Several agents work in one shared conversation. A chat manager chooses who speaks next. It suits review, debate and iterative refinement, where different roles comment on the same work.

Use when

  • You want several perspectives on one artefact.
  • Maker-checker review with distinct roles.

Watch out

  • Conversations can drift and loop. Limit turns.
  • Hard to test and audit. In regulated flows, prefer coded orchestration.

Sources: Microsoft Agent Framework: orchestrations [P]. Checked 18 Nov 2026.

2.9 · Control

The human gate

A person reviews at a set point and approves, corrects or rejects. Put gates where authority, accountability or low confidence demand it, and where actions cannot be undone. OpenAI's guide names two triggers for human intervention: exceeding failure thresholds and high-risk actions.

Design a good gate

  • Show the evidence with the proposal.
  • Make approve, correct and reject one click each, with a reason.
  • Capture corrections as data for evals and rules.

Watch out

  • Rubber-stamping: sample auto-approved items anyway, and track override rates.
  • Gates that see too much work become the bottleneck. Use confidence thresholds.

Sources: OpenAI: A practical guide to building agents (PDF) [P]. Checked 18 Nov 2026.

Part 3. Choosing a design

Two cards. A decision tree for agent, workflow or tool, and the live debate about multi-agent systems.

3.1 · Decision

Agent, workflow or tool?

Barry Zhang's checklist for building an agent

  • Complexity: is the task ambiguous enough that you cannot map the decision tree? If you can map it, build a workflow.
  • Value: does the outcome justify the extra cost? A budget of a few cents per task points to a workflow.
  • Capability: can the model do each critical step well enough today?
  • Cost of error: are mistakes cheap to find and fix? If not, limit autonomy and add review.

His three principles: do not build agents for everything, keep it simple, and think like your agent by looking at exactly what is in its context window.

Sources: How We Build Effective Agents, Barry Zhang (video, 15 min) [P]; talk page with slides [P]. Checked 18 Nov 2026.

3.2 · Debate

Single agent or multi-agent?

Two credible teams reached different conclusions for different problems. Know both sides.

The case for (Anthropic, research)

  • Anthropic's research feature uses a lead agent that starts parallel subagents to search.
  • On their internal research eval, a multi-agent setup beat a single agent by 90.2%.
  • It works well for breadth-first questions with many independent directions.
  • The cost: agents used about 4 times the tokens of chat, and multi-agent systems about 15 times.

The case against (Cognition, coding)

  • In June 2025, Cognition argued against multi-agent designs. Their principles: share full context, and remember that actions carry implicit decisions.
  • Parallel agents make conflicting choices that are hard to merge.
  • In April 2026 they reported multi-agent setups that do work in practice, such as review loops, while still doubting parallel-writer swarms.
SynthesisUse multiple agents for breadth: independent reads, searches and checks, each in its own context. Keep decisions that must agree in one place: one agent, or the orchestrator. Read-only subagents that report back are the safest form.

Sources: Anthropic: How we built our multi-agent research system [P]; Cognition: Don't Build Multi-Agents [P]; Cognition: Multi-Agents, What's Actually Working [P] (Apr 2026). Checked 18 Nov 2026.

Part 4. Building well

Six cards. What separates a demo from a system you can run: context, tools, memory, evals, observability and security.

4.1 · Context

Context engineering

Anthropic describes context engineering as the next step after prompt engineering. It covers everything in the window: system instructions, tools, MCP, examples, message history and retrieved data. Models have a limited attention budget. As context grows, recall falls, which Anthropic calls context rot. The aim is the smallest set of high-signal tokens that gets the result.

  • Instructions at the right altitude: clear heuristics, neither brittle if-then rules nor vague advice.
  • Few, distinct tools: if a human cannot tell which tool to use, the model cannot either.
  • Just-in-time retrieval: keep references and fetch details when needed.
  • Compaction: summarise old history and drop stale tool results.
  • Structured notes: the agent writes notes outside the window and reads them later.
  • Subagents: do detailed work in a separate context and return a short summary.

Sources: Anthropic: Effective context engineering for AI agents [P] (Sep 2025). Checked 18 Nov 2026.

4.2 · Tools

Designing tools for agents

Anthropic calls tools a contract between deterministic systems and non-deterministic agents. Design them for the model. A thin wrapper over every API endpoint works badly.

  • Choose the right tools to build, and leave out the ones the model does not need.
  • Namespace tools so their boundaries are clear.
  • Return meaningful context, such as names instead of opaque IDs.
  • Keep responses token-efficient: filter, paginate, truncate.
  • Write the tool description like a prompt. It is one.
  • Evaluate tools with realistic tasks, and let an agent help improve them.

Sources: Anthropic: Writing effective tools for agents, with agents [P] (Sep 2025). Checked 18 Nov 2026.

4.4 · Quality

Evals

An eval gives the system a task, grades the result and records a score. Agents work over many turns with tools, so the grade can look at the final outcome, the steps taken, or both.

Kinds

  • Capability evals: can it do the task at all?
  • Regression evals: did a change break something that worked?

Graders

  • Code: exact matches, tests, schema checks.
  • Model: an LLM judge with a rubric. Let it answer "unknown".
  • Human: a sample, to calibrate the others.
Start smallTwenty real cases with known answers beat a thousand synthetic ones. Write evals early. They force you to define success.

Sources: Anthropic: Demystifying evals for AI agents [P] (Jan 2026). Checked 18 Nov 2026.

4.5 · Operations

Observability and cost

  • Trace every run: model calls, tool calls, inputs, outputs, tokens, time, cost.
  • Set budgets per task with alerts and a hard stop.
  • Route by difficulty: small models for simple steps, large models only where needed.
  • Cache stable context. Batch work that is not urgent.
  • Make runs resumable from a checkpoint, so a failure does not restart a long task.
  • Report cost per task next to accuracy and time. A design that only looks good on one of the three is not finished.
4.6 · Security

Security for agents

Agents read untrusted content and act with real permissions. That combination creates new risks. In December 2025, OWASP published a Top 10 for Agentic Applications. Its highlighted threats include agent behaviour hijacking, tool misuse and exploitation, and identity and privilege abuse.

RiskControl
Prompt injection from documents, web pages or emailsTreat all external content as data. Separate it from instructions. Strip hidden text.
Tool misuseNarrow tool scopes. Validate tool inputs. Confirm destructive actions with a human.
Excess privilegeEach agent gets its own identity and the least privilege it needs.
Data leaksLimit what reaches the model. Control where outputs go.
Runaway behaviourStep, time and cost limits. A kill switch.

Sources: OWASP: Top 10 for Agentic Applications [P] (Dec 2025). Checked 18 Nov 2026.

Part 5. Protocols and frameworks

Two cards. The two open protocols, and the main frameworks with when to pick each. Framework details change fast, so check the docs before you commit.

5.1 · Protocols

MCP and A2A

MCP: agent to tools

  • A server exposes tools, resources and prompts. Clients connect agents to servers.
  • The current specification is 2026-07-28 ver. It sends the protocol version with each request. Revisions up to 2025-11-25 used a handshake at connection.

A2A: agent to agent

  • Agents publish an agent card (JSON) that describes their skills. Other agents find them and send tasks.
  • Google announced it in April 2025 and gave it to the Linux Foundation in June 2025.

They work at different layers and fit together: MCP for tools inside an agent, A2A between agents that belong to different systems or vendors.

Sources: MCP versioning [P]; A2A project [P]. Checked 18 Nov 2026.

  • Evaluator-optimizer: draft, grade, revise.
  • Human gate: authority and low confidence.

Building well

  • Smallest high-signal context.
  • Few, clear, well-described tools.
  • Evals from day one: code, model, human graders.
  • Trace everything. Budget every run.
  • All external content is untrusted.
