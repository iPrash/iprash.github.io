Enterprise Architect · Order sync review · Interview prep

Independent review of a quote-to-cash landscape

The client is a large distributor of physical products. Sales reps quote and order in Dynamics 365. MuleSoft and Azure Functions carry the order to an IBM order management system, then to Oracle ERP and the warehouse. Status flows back the same way. The real problem is order status that drifts out of sync: users change or cancel orders the warehouse is already working on. Your job is to review the current design, test the team's ideas, and recommend a way forward that the other systems can accept.

What the client wants from you
  • An end-to-end view. Nobody owns the whole order lifecycle across Dynamics, MuleSoft, the OMS, Oracle and the warehouse. There are no current architecture diagrams.
  • A fix for status mismatches. Not tuning. A change to how the systems agree on order state, without making everything synchronous.
  • Leadership communication. The client's leadership and lead architect own the decisions. You review, advise and present.
  • Teamwork with the specialists. A Dynamics team of 7–8 people knows the product. You bring the cross-system design.

Core · Triage

Can you explain it?

1. In one sentence, what is the client's problem?

Order state is committed in Dynamics first and then sent downstream asynchronously, so each system can hold a different status and users can change or cancel orders that the warehouse has already started. Card P5.

2. Which system should own the order after it is submitted?

The order management system. Dynamics owns the quote and the order until submit, then shows the OMS's view. Card S1.

3. Why not make every change synchronous?

The user would wait for the OMS, Oracle and the warehouse on every action, and one slow system would block sales. Use a confirmation step only for risky actions, such as cancel and quantity change after allocation. Card S8.

4. What is a "cancel requested" state?

The user's cancel is recorded as a request. The order shows "cancel requested" until the system that owns the order confirms or rejects it. Card S3.

5. Oracle rejects a cancel because the order is picked. What must happen next?

The rejection must flow back as an event. Dynamics and the OMS undo their cancel, show "cancel rejected, shipping", and alert the rep. Today the rejection is lost. Card S3.

6. How do you stop a stale screen from overwriting newer data?

Optimistic concurrency: every update carries the version it was based on. Dataverse supports this with ETags and If-Match, which return 412 when the record changed. Card S4.

7. A "picked" event arrives after a "shipped" event. What do you do?

Ignore it. Status may only move forward in the lifecycle. Use a sequence number or event time per order. Card S5.

8. What is the quick win for the first 30 days?

A daily reconciliation of order status across Dynamics, the OMS and Oracle, with a list of mismatched and stuck orders. It sizes the problem and finds the worst cases. Card S7.

9. What is a backorder?

A quantity that cannot ship now because stock is short or damaged. It stays open to ship later, or is cancelled. Card F3.

10. Salesforce Apex trigger: what is it called in Dynamics?

A plug-in: server code that runs on a table event. Card F2.

11. What happens when a Dataverse webhook endpoint returns 500?

It fails without a retry. Only 502, 503 and 504 get one retry. An asynchronous webhook records the failure in a system job, and nothing replays it. Card S6.

12. Who decides on the target design?

The client's leadership and lead architect. You review, recommend and present options with trade-offs. Card F4.

Core · P4

What the team has tried

BRIEFING For some actions, such as cancel, the team changed the order of events. Dynamics sends the cancel request first, waits for the downstream acknowledgement, and only then commits the cancel. It works. The business does not accept it everywhere, because users wait longer and some screens become slow.

What it gets right

  • The system that knows the true state decides.
  • No local commit that has to be undone later.
  • It is the right pattern for high-risk actions.

Why it does not generalise

  • The user waits for the slowest downstream system.
  • If a system is down, the user is blocked.
  • Every system must answer fast, which changes their contracts too.
  • Many changes are low risk and do not need it.
Your positionAgree with the pattern and its limits. The missing piece is a rule for where to use it: a decision matrix by action and order state (S8), plus a non-blocking version for when the user should not wait (S3). This turns a one-off fix into a design standard.
Say this"Confirm-then-commit is the right pattern for cancel. The question is where else to use it. I would build a simple matrix of action by order state, decide per cell, and give the user a 'requested' status when they should not have to wait."

Core · S1

One owner per lifecycle phase

At any moment, exactly one system is the authority for an order's state. Ownership passes along the lifecycle. Other systems show a copy and ask the owner before acting.

  • Why the OMS: it already orchestrates fulfilment, and IBM's product has per-status modification rules that say which changes are allowed in which status.
  • What changes for Dynamics: after submit, it stops committing state changes on its own. It shows the OMS status and sends change requests (see S3).
  • What changes for the OMS: it must hear from Oracle quickly enough that its own status is trustworthy, or it must ask Oracle before it accepts risky changes.
The catch in scenario 2In the cancel case, the OMS also said "allocated" while Oracle was already processing. So an ownership rule is not enough on its own. The owner's status must be fresh, or the owner must confirm with Oracle before accepting a cancel.
Say this"The first design decision is ownership. Before submit, Dynamics owns the order. After submit, one system, probably the OMS, is the truth, and Dynamics shows its view and sends requests. Without that rule, every other fix is a patch."

Core · S3

Requested states: record the intent, then confirm

A non-blocking version of confirm-then-commit. The user's action is saved at once as a request. The order shows "cancel requested" or "change requested". The owner system confirms or rejects. The user does not wait on screen, and nothing is committed until the owner agrees.

Why it fits this client

  • Users are not blocked, so the business objection to confirm-then-commit goes away.
  • The truth is decided once, by the owner.
  • Rejections become visible, which fixes scenario 2.

Design points to agree

  • Credit: release the credit hold only when the cancel is confirmed. Agree this with finance.
  • Timeout: if no answer within [N] minutes, alert support.
  • Compensation: a rejected change must undo any partial updates (a saga).
Answer to the earlier objectionIn the briefing, an online-retailer style "cancel request accepted, we will confirm" was pushed back because of payments and credit. The requested-state pattern answers that: credit is released only when the cancel is confirmed, so finance never acts on an unconfirmed cancel.
Say this"I would not make the user wait. Save the cancel as a request, show 'cancel requested', and let the owner confirm or reject. Credit is released only on confirmation. And a rejection updates every system, so we never ship an order that Dynamics says is cancelled."

Core · S4

Versioning: reject changes made on a stale view

Every order carries a version number. A change request says which version it was based on. If the order has moved on, the change is rejected and the user sees the current state. This is optimistic concurrency, and it fixes scenario 1.

  • Inside Dynamics: Dataverse supports this today. Each record has an ETag. An update sent with If-Match fails with 412 if the record changed in the meantime.
  • Across systems: the OMS order version, or the last status sequence number, travels with every change request. The OMS rejects a request based on an older version.
  • For the user: "This order changed while you were editing (backordered 1). Review and resubmit."
Say this"Scenario 1 is a classic lost update. Each change should carry the version it was based on. If the order changed in the meantime, the change is rejected and the rep sees the new state. Dataverse already supports this with ETags. The OMS needs the same check."

Sources: [P] Dataverse Web API: conditional operations (ETag, If-Match, 412). Checked 4 Nov 2026.

Core · S5

Event ordering and idempotency

Ordering

  • Status only moves forward. Ignore a "picked" update that arrives after "shipped".
  • Each update carries a sequence number or event time per order.
  • Keep updates for one order in order: one queue partition or message group per order.
  • Anypoint MQ FIFO queues keep order within a message group (for example, the order number).

Idempotency

  • Every message has a unique ID. Receivers ignore duplicates.
  • Retries and replays are then safe.
  • In MuleSoft: Idempotent Message Validator with a persistent object store.
  • In Dataverse: alternate keys and upsert.
Gotchas
  • Anypoint MQ FIFO: once a message moves to a dead-letter queue, strict order in that group is no longer guaranteed.
  • FIFO queues are capped at 300 transactions a second. Fine for status updates; check at peak.
Say this"Status updates need two guarantees: they never go backwards, and duplicates do no harm. A sequence number per order, a forward-only rule at the receiver, and idempotent consumers. MuleSoft has both tools: FIFO message groups and the idempotent validator."

Sources: [P] Anypoint MQ queues: FIFO, message groups, limits; [P] Idempotent Message Validator. Checked 4 Nov 2026.

Core · S7

Reconciliation and an exceptions view

The quickest win. Compare order status across Dynamics, the OMS and Oracle every day, or every hour for open orders. List every mismatch and every order stuck in one state too long.

  • It sizes the problem. "312 orders out of sync last week, 40 of them cancelled-but-shipped" is a number leadership can act on.
  • It finds the worst cases first. The list shows which transitions break most.
  • It proves the later fixes work. The mismatch count is the success measure.
  • It needs no change to the order flow. It can run in weeks 2–4 of the review.
Say this"Before any redesign, I would want a daily reconciliation across the three systems. It tells us how big the problem is, where it breaks, and later whether the fix worked. It is cheap and it changes nothing in the live flow."

Core · A1 · Frame

Scope, charter and independence

A review fails most often in week 1, when the questions are vague and access is slow. Write a one-page charter and get the sponsor to sign it before you interview anyone.

The charter, one page

  • Questions to answer. Are the team's findings right? What risks and gaps did they miss? Will the proposed resolution work? What should happen next?
  • Scope. CRM, CPQ, OMS, ERP, MuleSoft, other middleware, named downstream systems. Out of scope: say it out loud, such as data migration or licensing.
  • Deliverables and dates. Interim view at week 2 or 3. Final report and read-out at the end.
  • Sponsor and steering group. Who receives the report. Who decides.

Independence terms

  • Read access to all artefacts, code, configuration and monitoring.
  • Access to all people, including vendors and the support team.
  • The delivery team can correct facts. It cannot edit conclusions.
  • You report to the sponsor. The team you review sees the draft to check facts.
  • Disagreements are recorded in the report, with both views.

Stakeholders to interview

The client's lead architect and the senior leaders who raised the concern · Dynamics team and its architect · MuleSoft platform owner · OMS team · Oracle ERP and warehouse teams · pricing, product and inventory service owners · support (they know where it really breaks) · two or three sales reps and order-desk users.

From the briefingThe client's leadership and lead architect own the design and the decisions. You review and advise. Make that explicit in the charter, so nobody expects you to take over the design.
Gotchas
  • Slow access eats a short review. Ask for the access list in the first meeting, with names against each item.
  • A scope without "out of scope" grows every week.
  • If the sponsor wants a predetermined answer, find out in week 1. Say how you will handle it.
Say this"Before I interview anyone, I agree a one-page charter with the sponsor: the questions we answer, the scope, the dates, and my independence terms. Read access to everything, access to everyone, and the team can correct my facts but not my conclusions."

Extra · A2 · Structure

ATAM, quality-attribute scenarios and the utility tree

ATAM is the SEI's method to evaluate an architecture against the qualities the business needs. A full ATAM takes several days of workshops. In a short review, run a light version: two workshops that build a utility tree and test the top scenarios against the architecture.

ATAM outputs

  • Risks: decisions that may cause a quality goal to fail.
  • Non-risks: decisions that are sound. Record them. They build trust with the team.
  • Sensitivity points: one setting that strongly drives one quality, such as the MuleSoft retry count.
  • Trade-off points: one setting that drives two qualities in opposite directions, such as confirm-then-commit on cancel (consistency up, speed and availability down).

Light ATAM in a 6-week review

  1. Business drivers from the sponsor (week 1).
  2. Architecture walk-through by the team (week 1).
  3. Utility tree workshop: list scenarios, rank by business value and difficulty (week 2).
  4. Analyse the top 6–10 scenarios against the C4 views and the evidence (weeks 2–4).
  5. Present risks, non-risks, sensitivity and trade-off points (read-out).

Extra · A5 · Measure

Baseline: mismatch rate, status lag and latency

For this client the main baseline is consistency: how many orders are out of sync, and how long a status takes to travel from the warehouse back to Dynamics (status lag). Latency still matters for the quote screens. Measure both, end to end, at normal load and at peak.

The five transactions

  1. Quote save and price recalculation
  2. Quote submit for approval
  3. Quote to order (CRM to OMS)
  4. Order to ERP (OMS to Oracle)
  5. Status and invoice back to CRM

For each: P50, P95 and P99 latency, throughput per minute, error rate, and the same at peak (month-end, quarter-end).

Tools for the math

  • Little's law: concurrency = throughput × latency. Use it to compare load with concurrency limits.
  • Utilisation: queues grow sharply above about 70–80% busy. A component at 90% at peak is a risk even if it works today.
  • Volumetrics: business drivers (quotes, lines per quote, orders) times calls per driver gives load per hop. This is your scale-modelling method from Story B.
Gotchas
  • Averages hide the problem. Users feel P95 and P99.
  • Test data with 5 quote lines will not show a problem that appears at 300 lines. Use the real distribution of quote sizes.
  • One shared integration user funnels all calls into one set of per-user limits. Check which identity each integration uses.

Core · A6 · Validate

Extra · B2 · Pattern risk

Chained synchronous calls

A user clicks "submit". CRM calls CPQ, which calls MuleSoft, which calls the ERP for a credit check and the OMS for stock. The user waits for the slowest path. Latency adds up along the chain. Availability multiplies: five hops at 99.9% each give about 99.5%.

Symptoms

  • Timeouts at the user interface at peak.
  • A slow downstream system makes upstream systems slow too.
  • Plug-ins or flows that call external services inside a save.

Fixes

  • Keep only what the user must see now in the sync path.
  • Make the rest asynchronous with a status the user can see.
  • Cache reference data (price lists, products) close to the caller.
  • Set timeouts that shrink along the chain, so the caller gives up last.
Gotchas
  • A synchronous Dataverse plug-in that calls out runs inside the database transaction and holds locks while it waits. It also counts against the 2-minute limit.
  • If each hop has a 30-second timeout, the outer caller times out first and retries while the inner call still runs.
Say this"In a synchronous chain latency adds and availability multiplies. I keep only what the user must see in the sync path and move the rest to a queue with a visible status. Timeouts shrink along the chain, so the outer caller gives up last."

Extra · B3 · Landscape risk

Point-to-point sprawl, and too many layers

With direct links between systems, each new system adds links to many others. Eight systems can need up to 28 links. Each link has its own mapping, security and error handling. API-led connectivity reduces this by putting reusable system APIs in front of each system of record.

The opposite failure also exists. Some estates route every call through experience, process and system APIs even when one hop would do. Each layer adds a network call, a payload transform and a place to fail.

How to confirm

  • Count interfaces per system from the Mule app list and the CRM and ERP configuration.
  • Look for direct calls that bypass MuleSoft: Power Automate HTTP actions, plug-ins with URLs, custom services.
  • Count Mule hops per user transaction in the traces.

Fixes

  • One system API per system of record. Everything else calls it.
  • Collapse layers that add no logic for high-volume, latency-sensitive calls.
  • An interface catalogue with owner, volume, pattern and SLA.
Say this"I check for both extremes: point-to-point links that bypass the platform, and calls that pass through three Mule layers when one adds all the value. The test is simple: each layer must earn its latency."

Extra · B5 · Failure risk

Retry storms

A retry helps when a failure is brief. It hurts when the target is overloaded. If three layers each try a failed call three times, one user action can send 27 calls to the last system. The system that was slow is now down.

Symptoms

  • Error rates jump suddenly after a small slowdown.
  • 429 or 503 counts climb with traffic flat.
  • Duplicate records after an incident.

Fixes

  • Retry at one layer only, usually closest to the target.
  • Exponential backoff with jitter. Honour Retry-After.
  • A retry budget: no more than a fixed share of calls may be retries.
  • A circuit breaker that fails fast when the target is down.
  • Never retry a non-idempotent call without an idempotency key.
Gotchas
  • In MuleSoft, check Until Successful scopes, connector reconnection strategies and the caller's own retries. They stack.
  • Retries also cost money on usage-based MuleSoft plans and count against Power Platform request limits.
Say this"I count retries across all layers, because they multiply. One retry layer, exponential backoff with jitter, honour Retry-After, a circuit breaker, and no retries without an idempotency key."

Extra · C1 · Order management

IBM order management: statuses and modification rules

The client runs an IBM order management system ver, most likely IBM Sterling Order Management. It takes the order from Dynamics, validates it, allocates stock and orchestrates fulfilment across Oracle and the warehouse.

What matters for the sync problem

  • Statuses are numbered and move along a pipeline, from created through scheduled, released, shipped and beyond.
  • Modification rules say, for each change type and each status, whether a change is allowed, disallowed or ignored.
  • A change is blocked if any applicable status is set to disallow.
  • Cancel works only inside a system status range (for a sales order, statuses 1000 to 3350). You can narrow that range. You cannot widen it.
  • Holds stop processing. A hold type can resolve itself when the order is cancelled.
  • Users with the right permission can override disallowed changes in the consoles. Ask who has it.

Questions to ask the OMS team

  • Which product and version, on premises or cloud?
  • How do Oracle and the warehouse report status back, and how fast?
  • What happens when Oracle rejects a change the OMS already accepted?
  • Which modification rules are configured for cancel and quantity change?
  • Can the OMS carry a version number and a correlation ID on every message?
The key pointIBM's own guidance warns to "contemplate business and system integration implications" before allowing a normally disallowed change. In scenario 2, the OMS allowed a cancel based on its own status, which was behind Oracle's. The rules are only as good as the status they read.
Say this"The OMS already has modification rules per status, so the business logic for what can change exists. The questions are whether its status is fresh enough, whether Dynamics uses the same rules, and what happens when Oracle disagrees."

Extra · C7 · Azure glue

Azure Functions and Service Bus in this landscape

Here Azure is glue on the Dynamics side: a webhook calls an Azure Function, which calls a MuleSoft API. That hop has no queue of its own.

  • Risk: if the Function or MuleSoft is down, the update fails. Retries are limited. Nothing replays it.
  • Option 1: Dataverse posts the event to Azure Service Bus through a service endpoint. The Function, or MuleSoft, reads from the queue. Service Bus has sessions for ordering, duplicate detection and a dead-letter queue.

Extra · Quick-fire, platform

Platform questions, one-line answers

What is a plug-in, and when does it run?

Server code on a Dataverse table event. Synchronous plug-ins run in the user's request; pre- and post-operation ones are inside the transaction. Asynchronous ones run after commit. C3.

What happens when a webhook endpoint is down?

Synchronous: the save fails for the user. Asynchronous: the failure is logged in a system job; one retry only for 502, 503 or 504; nothing replays it. C3.

How does Oracle decide whether a change is allowed?

Processing constraints. After pick confirm, cancel, delete and split are blocked by default. C2.

How does the IBM OMS decide whether a change is allowed?

Modification rules: allow or disallow per change type and per status. Cancel works only inside a status range. C1.

How do you keep messages for one order in order in MuleSoft?

An Anypoint MQ FIFO queue with the order number as the message group. S5.

Walkthrough: the cancel-during-processing case

Practise this in 30 minutes on a blank page, out loud. It covers the problem, your method and the solution patterns together.

Core · Practice case

"A rep cancels an order. The OMS accepts. Oracle has already started. The order ships."

Assume: as in P3. Credit stays held. The team's idea is to make cancel synchronous everywhere.

1–2 · Clarify and map
  • Ask: how often does it happen? What does each one cost? How do status updates travel back, and how fast?
  • Draw the four lifelines: Dynamics, MuleSoft, OMS, Oracle and warehouse. Draw the cancel and the rejection (see P3).
3 · Root causes
  • The cancel was allowed on a stale status (Dynamics and the OMS both behind Oracle).
  • The cancel was committed before the owner agreed.
  • Oracle's rejection was not an event that upstream systems acted on.
  • Credit was tied to the "cancelled" status, which was false.
4 · Options
OptionGainCost
Synchronous cancel everywhereCorrectUsers wait; blocked when a system is down. The business already said no
Cancel requested + owner confirms with Oracle + rejection eventCorrect, and users don't waitNew state in Dynamics and the OMS; rejection events from Oracle
Block cancel in Dynamics after release, using the status feedQuick, cheapOnly as good as the status lag
Detect and repair (reconciliation)Visible, no flow changeFinds problems after the fact
5 · Recommendation and roadmap
  • Now: reconciliation and an alert on cancelled-but-shipped; block cancel in Dynamics after release.
  • Next: cancel requested, owner confirms, rejection as an event, credit released only on confirmation.
  • Then: extend the same pattern to other risky changes through the allowed-actions table.
6 · Risks and open questions
  • Can Oracle and the OMS send rejection events? Effort for those teams.
  • What the rep sees if no answer arrives: timeout rule and alert.
  • Finance's rule for releasing credit.
GotchaDo not jump to the answer. The panel scores how you get there. Say "I would expect" and "I would check". Avoid "the answer is".

Their problem in one breath

Dynamics commits first and tells the others later, and it gates actions on its own stale status. So users edit or cancel orders the warehouse already has, and Oracle's "no" never flows back. Orders ship after cancel, credit stays held, returns follow.

Answer frame

Play back → Owner → Pattern → Trade-off → Next step

Gap line

"No hands-on Dynamics or ERP. My strength is how systems agree on state through middleware. Your Dynamics team has the product depth."

First deliverables

Status map · allowed-actions table · five traced orders · daily reconciliation.

The patterns

  • One owner per phase: Dynamics to submit, then the OMS
  • Shared state model + allowed actions
  • "Cancel requested": confirm, don't wait
  • Rejection is an event
  • Version check (ETag, If-Match → 412)
  • Forward-only, ordered, idempotent status
  • Durable first hop, DLQ, replay
  • Reconciliation as the quick win
